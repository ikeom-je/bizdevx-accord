# bizdevx プロセスフロー・ナレッジ

bizdevx 標準プロセス(サービス企画 + AI 駆動開発ライフサイクル)の設計思想と実践知見を、AI 駆動開発で広く知られる進め方と、一般化した実践経験のエッセンスとして整理したもの。プロセステンプレート YAML(`templates/bizdevx-standard.yaml`)のチェックリスト・変革視座・エスカレーション案内の出典となる。

**本アプリ固有の狙いは「ロール間の断絶を埋める」ことにある。** AI が成果物を高速に作れるようになるほど、企画・開発・ビジネスの各ロールが分業したまま並走し、互いの意思決定に必要な文脈を渡し損ねやすくなる。bizdevx 標準プロセスは、この断絶が起きやすい節目に**モブ(複数ロール同席の意思決定)**と**同席の記録**を意図的に組み込むことでこれに対処する。

## 1. 基本思想

AI 駆動開発は、AI エージェントが成果物を作成し、人間が意図の提示・レビュー・承認に集中することでリードタイムを極小化する開発手法である。ツールやプロンプトのテクニック集ではなく考え方であり、真価はプロジェクトの文脈に応じて進め方をテーラリングし続けることで発揮される。

3つの設計原則(bizdevx はここに4つ目を加える):

1. **価値駆動の要件定義** — ユーザーから見える価値を起点にストーリーを定義する。非機能要件・技術スタック・見積もりなどの技術的決定は後ろ倒しにする。AI が生成しがちなエッジケースや過剰要件は早期に削ぎ落とし、最小の価値提供に集中する。
2. **本質的複雑性へのフォーカス** — アーキテクチャコンポーネントに依存しないピュアなドメインモデルを先に作り、ビジネスドメイン固有の複雑さに集中する。偶発的複雑性を排除する。
3. **段階的なアーキテクチャ詳細化** — ドメインモデル実装後に、デプロイ先に応じた必要最小限のアーキテクチャコンポーネントを追加する。
4. **ロールを越えた同期(bizdevx の力点)** — 重要な意思決定の節目では、影響を受ける全ロールが同席して合意する。分業と引き継ぎに任せると、企画意図が開発に伝わらない・開発の制約が企画に還元されない、という乖離が起きる。

## 2. 統制の仕組み

重要な判断はすべて人間の明示的な確認を通す、という統制原則を採る。

- **質問ファイル駆動**: AI は曖昧点を口頭チャットでなく質問ファイル(Q&A 形式)に書き出し、人間が回答してから再開する。決定が文書として残る。
- **計画 → 承認 → 逐次実行**: AI にまず作業計画(チェックボックス付き)をファイルに書かせ、人間がレビュー・承認してから 1 ステップずつ実行させる。完了ごとにチェックを付けさせる。
- **段階的承認ゲート**: 各フェーズの成果物を人間が検証してから次へ進む。ゲートは**コンテキストリセットの最適な分岐点**でもある: 必要な文脈はファイルに出力済みのため、AI ツール側の会話コンテキストを毎ゲートで初期化して品質を保つ。
- **監査証跡**: 進捗状態と操作履歴をファイル(状態ファイル・監査ログ)として自動的に残す。
- **同席の記録(bizdevx 独自)**: mob 実施のステージには「誰が同席して決めたか」を記録し、特定ロールだけで意思決定が完結していないかを可視化する。

## 3. フェーズの流れ

```
Phase 0: 企画(Working Backwards)  《mob: 企画・ビジネス・開発の全ロール》
  ペルソナ深掘り → 注力課題の選定 → PRFAQ + KGI/KPI + スコープ(In/Out)
Phase 1: Inception  《mob: アーキテクト主導+PM・ビジネスオーナー立ち会い》
  ユーザーストーリー → 画面モック → Unit of Work(境界づけられたコンテキスト)
  → コンテキストマップ → Unit 間 I/F 契約(OpenAPI / 消費者駆動契約)
Phase 2: Construction(Unit 単位で並列)  《ドメインモデリングは PM 立ち会い》
  ドメインモデリング → コード → テスト → アーキテクチャ追加
Phase 3: 統合・レビュー  《mob: QA 主導+開発・ビジネスオーナー立ち会い》
  QA/受け入れ → ユーザーレビュー → 次サイクルへ
```

深さの使い分け: 全ステージを毎回フルで回すのではなく、課題の複雑さに応じた深さで回す。PoC・小規模改修は軽く、既存システム改修はリバースエンジニアリングを厚く、基幹系は非機能設計とテストを厚く取る。

## 4. ステージ別の実践知見

### ユーザーストーリー計画
- ユーザーから見えない部分は削ぎ落とす(それは Construction で扱う)。
- 複雑なビジネスルールはストーリー定義の**後**に与える。先に与えると AI がそれに引っ張られ過剰設計しがち。
- 既に具体化済みの要件がある場合は、詳細化が必要な箇所だけを AI に渡す。
- ストーリー作成後に HTML モックを出力させると、動くものベースで確認できる。
- **ストーリーが 20 を超えたら赤信号**: レビュー負荷と Unit 数が膨らみ、1 Unit も完成しないリスクが高まる。スプリントを複数回すことを前提に MVP スコープを狭める。

### Unit of Work
- 境界づけられたコンテキストで分割する(Unit を跨ぐと用語の意味が変わる)。
- 責務に加えチームのリソースも考慮する。AI の提案が過度に細かい場合は統合を検討。
- 境界の定義が目的であり、API 設計やコード実装に踏み込ませない(AI は先行しがち)。
- コンテキストマップ(Mermaid)で Unit 間の依存の強弱・方向を可視化する。
- 既存コード改修では、コード全体でなく「階層構造と責務を記述したドキュメント」(AI に作らせる)を渡す。リポジトリを跨ぐ改修 Unit は AI が混乱するため避け、リポジトリ単位で Unit を切る。
- **分割の節目にはアーキテクトだけでなく PM・ビジネスオーナーが立ち会う**。事業上の優先度と技術的な境界がずれていないかをその場で確認する(bizdevx の狙い)。

### ドメインモデリング / コード
- アーキテクチャコンポーネントとコードを生成させない段階を明確に分ける(モデリング時はモデルのみ)。
- コード生成はシンプル・フラット構成・インメモリリポジトリ前提から始める。
- TDD を活用するとテストコードがコードの使用例になり、レビューが容易になる。
- **ドメインモデリングには PM の立ち会いを推奨する**。業務用語・ルールの解釈をエンジニアだけで決めてしまうと、後工程で企画意図とのずれが発覚しやすい。

### 設計変更の規律(Vibe Code 回避)
- 設計ドキュメントを迂回した直接コード編集は、設計と実装の乖離を生み後続ステップを混乱させる。正しい手順は「設計を更新 → コードを再生成」。
- コード生成中に判明した設計判断は、要件・ユーザーストーリーへ**逆方向に伝播**させる(影響がないか毎回確認する)。
- 影響を知りたいだけのときは「何も変更せず、この案の影響を評価せよ」と明示する。

## 5. AI との対話・コンテキスト管理の技法

- AI は提案を肯定しがち。クローズドクエスチョンで単一案を見せると何でも肯定するため、オープンクエスチョンにするか複数案を併記して比較させる。
- 選択肢形式の質問(A/B/C)を AI に作らせると人間の回答負荷が下がり、意思決定が滞留しにくい。
- 無関係な情報がコンテキストにあると AI がそれに引っ張られる。使わない情報・ツールは渡さない。
- 長いプロンプトの中間は無視されやすい。冗長な情報を減らし、ゲートごとにコンテキストをリセットする。
- 事前に「ビジョン文書(何を・なぜ)」と「技術環境文書(ツール・制約・禁止事項)」を用意しておくと、AI からの確認質問が激減する。
- AI を 5 分以上遊ばせているなら壁打ち相手として使う。

## 6. モブによる同期的意思決定(bizdevx の中核)

AI の生成速度に人間の合意形成が追いつかずボトルネック化するのが最大の実践課題。対策はステークホルダー(企画・PM・開発・QA)が同席し、AI への指示・レビュー・意思決定を同期的に行う**モブワーク**である。

企画フェーズに開発者が、Construction にビジネスサイド(PM)が参加することで、フェーズ間のロール断絶と手戻りを防ぐ。同席の有無・参加ロールの構成は記録として残し、特定のロールだけで意思決定が完結し続けていないかを継続的に点検する(全体進捗ボードの分業化シグナル)。
