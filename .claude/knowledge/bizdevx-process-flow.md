# bizdevx プロセスフロー・ナレッジ

bizdevx 標準プロセス(サービス企画+AI 駆動開発)の設計思想を整理したもの。プロセステンプレート YAML(`templates/bizdevx-standard.yaml`)のチェックリスト・変革視座・エスカレーション案内の出典となる。

一般に知られる AI 駆動開発の実践知見(AI に成果物を作らせ、人間は意図の提示・判断・監督に集中する進め方)を土台にしつつ、**本アプリ固有の狙いは「ロール間の断絶を埋める」こと**にある。AI が生成物を高速に作れるようになるほど、企画・開発・ビジネスの各ロールが分業したまま並走し、互いの意思決定に必要な文脈を渡し損ねる場面が増える。bizdevx 標準プロセスは、この断絶が起きやすい節目を特定し、そこに**モブ(複数ロール同席の意思決定)**と**構造化された記録**を意図的に挟み込むことで解決する。

## 1. 基本思想

1. **価値駆動の要件定義** — ユーザーから見える価値を起点に定義する。非機能要件・技術スタック・見積もりなどの技術的決定は後ろ倒しにし、最小の価値提供に集中する。
2. **本質的複雑性へのフォーカス** — ビジネスドメイン固有の複雑さに集中し、技術的な作り込み(偶発的複雑性)を後段に回す。
3. **段階的な詳細化** — 大枠を固めてから、デプロイ・運用に必要な要素を必要最小限だけ足していく。
4. **ロールを越えた同期(bizdevx の力点)** — 重要な意思決定の節目では、影響を受ける全ロールが同席して合意する。分業と引き継ぎに任せると、企画意図が開発に伝わらない・開発の制約が企画に還元されない、という乖離が起きる。

## 2. 統制の仕組み

重要な判断は人間の明示的な確認を通す、という統制原則を採る。

- **構造化された意思決定記録**: 曖昧な点は口頭のやり取りに流さず、質問と回答をファイルとして構造化して残す。決定の経緯が後から追跡できる。
- **計画→承認→逐次実行**: 作業計画をチェックリスト形式で先に示し、レビュー・承認を経てから一段階ずつ進める。
- **節目でのリセットと検証**: 各フェーズの成果物を人間が検証してから次に進む。節目は思考のリセットポイントでもあり、必要な文脈はすでに文書化されているという前提で、その都度フラットな状態から確認し直す。
- **監査証跡**: 進捗状態と操作履歴を自動的に記録として残す。
- **同席の記録(bizdevx 独自)**: 重要な意思決定の節目に「誰が同席して決めたか」を記録し、特定ロールだけで意思決定が完結していないかを可視化する。

## 3. フェーズの流れ

```
Phase 0: 構想    《同席》企画・開発・ビジネスの全ロールで、顧客課題とゴール指標を固める
Phase 1: 設計    《同席》開発リードが主導しつつ、企画・ビジネス側が立ち会って作業境界とインターフェースを決める
Phase 2: 実装    ユニットごとに開発が進行。ドメインの構造化は企画側の立ち会いを伴う
Phase 3: 検証    受け入れ・レビューを経て次サイクルへ
```

深さの使い分け: 全工程を毎回フルで回すのではなく、課題の複雑さに応じた深さで回す。小規模な検証は軽く、既存システムの改修は現状分析を厚く、基幹系は非機能設計と検証を厚く取る。

## 4. 進行上の実践知見

### 構想フェーズ
- 顧客像を先に深掘りしてから課題を絞り込む。解決策の検討はその後にする。
- ゴールは顧客価値の言葉で一文にまとめ、測定指標とその測定方法をセットで定義する。「やらないこと」も同時に明示する。
- **このフェーズは企画・ビジネス側だけで進めない**。開発側が同席することで、実現性の制約が構想の段階から反映される。

### 要件・作業単位の整理
- ユーザーから見える価値だけに絞る。作り込みすぎた要件は数が多いほどレビュー負荷と後工程のリスクを増やすため、まとまりが一定数を超えたら分割・絞り込みを検討する信号とする。
- 複雑な業務ルールは、要件の骨格を固めた**後**に反映する。先に与えると、その情報に引っ張られて過剰な作り込みになりやすい。
- 要件を確認できる簡易な画面イメージを早期に作ると、認識合わせが進む。

### 作業単位への分割
- 作業単位は、意味のまとまり(用語や概念が一貫する範囲)で区切る。単位を跨ぐと同じ言葉でも意味合いが変わることがある。
- 責務だけでなく、実際に動けるチームのリソースも考慮して分割の粒度を決める。
- 分割の目的は境界を決めることであり、この段階で内部設計や実装の先取りをしない。
- 単位間の依存関係は、関係図として可視化しておくと後工程の調整がしやすい。
- 既存システムを対象にする場合は、コード全体を渡すのではなく、構造と責務を要約したドキュメントを用意してから分割を検討する。対象範囲がリポジトリをまたぐ場合は、リポジトリ単位で作業単位を分けるのが安全。

### 内部設計・実装
- 内部構造の設計と実装(コード生成)は明確に段階を分ける。設計段階では実装の先取りをさせない。
- 実装は、まずシンプルな構成(フラットな配置・簡易な永続化)から始め、動作確認できる最小の形を優先する。
- 挙動を先にテストとして記述しておくと、レビューする側が使い方を把握しやすくなる。

### 設計と実装の一貫性を保つ規律
- 設計文書を経由せず直接コードだけを変更すると、設計と実装がずれていき後工程で混乱を招く。変更は「設計を更新→実装に反映」の順で行う。
- 実装中に判明した設計上の決定は、上流の要件・設計文書にも反映されているか確認する(下流での気づきを上流に戻す)。
- 影響範囲だけを先に把握したい場合は、「変更せず影響のみを評価する」よう明確に指示する。

## 5. 対話・作業指示の技法

- 単一案を見せて意見を求めると、追従した回答が返りやすい。複数案を並べて比較させる、またはオープンな問いかけにすることで、中立的な判断材料を引き出す。
- 判断が必要な問いは選択肢形式で用意すると、回答する側の負荷が下がり、意思決定の停滞を防げる。
- 作業に関係のない情報は渡さない。無関係な文脈が判断に影響することがある。
- 長い指示ほど中間部分が読み飛ばされやすい。冗長な情報を削り、節目ごとに文脈をリセットする。
- 事前に「目的・背景」と「制約条件」を簡潔な文書として用意しておくと、後から生じる確認の往復が大きく減る。

## 6. モブによる同期的意思決定(bizdevx の中核)

生成物を作る速度が上がるほど、人間側の合意形成が追いつかずボトルネックになりやすい。これへの対策が、影響を受けるロール(企画・ビジネス・開発・検証)が同席し、指示・レビュー・意思決定を同期的に行う**モブ**である。

構想フェーズに開発側が、設計・実装フェーズにビジネス側が同席することで、フェーズ間でロールが分業したまま進み、互いの知見・制約・意図が伝わらないまま次工程に渡ってしまう事態を防ぐ。同席の有無・参加ロールの構成は記録として残し、特定のロールだけで意思決定が完結し続けていないかを継続的に点検する。
