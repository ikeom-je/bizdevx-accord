# BizDevX Accord ユーザーストーリー

- ステータス: レビュー中
- 対応 spec: [bizdevx-accord-design.md](bizdevx-accord-design.md)
- 方針: bizdevx 標準プロセスの流儀に従い、価値起点・受け入れ基準つき・20個以内に絞る。各ストーリーは spec の課題マップ(A〜J)にトレースする。

## Phase 0 / プロジェクト立ち上げ

### US-01 プロジェクト作成 〔課題C〕
**ファシリテータ**として、深さプロファイル(PoC / 新規サービス / 既存改修)を選んでプロジェクトを作成したい。チームの状況に合った厚さのプロセスで始めるため。

- [ ] 3つの深さプロファイルから1つを選んで作成できる
- [ ] 作成時にプロセステンプレートのバージョンが固定され、以後のテンプレート変更の影響を受けない
- [ ] メンバーの登録とロール(複数可)の割り当てができる

### US-02 チーム憲章への合意 〔課題J〕
**チームメンバー**として、プロジェクト開始時に AI ネイティブな働き方の憲章を確認・合意したい。従来ワークフローの単なる高速化に陥らないため。

- [ ] Phase 0 冒頭のステージとして憲章項目(視座転換表ベース)が提示される
- [ ] メンバーごとに合意が記録される
- [ ] 合意後、憲章はどの画面からも1クリックで参照できる

### US-03 ステージガイドで作業する 〔課題A・C・H・J〕
**ステージ担当者**として、ステージの目的・変革視座・コンテキスト準備チェック・プロンプト集・完了チェックリストを1画面で見たい。知見レベルに依らず一定品質で進めるため。

- [ ] ステージの目的と変革視座(従来との違い・捨てる旧習慣)が冒頭に表示される
- [ ] プロンプトには「目的」「修正するときの観点」が併記され、コピーボタンがある
- [ ] コンテキスト準備チェックが未完了の場合、その旨が警告表示される
- [ ] チェックリスト項目に良/悪例が表示される
- [ ] 成果物リンク(URL)を登録し、ステータスを変更できる

## ゲートと承認

### US-04 PRFAQ 確定ゲート(G1) 〔課題A・F〕
**ビジネスオーナー**として、品質チェックリスト完了済みの PRFAQ を、理解確認をした上で承認したい。ゴール品質を属人性から切り離すため。

- [ ] チェックリスト未完了の状態では承認操作ができない
- [ ] 承認時に理解確認3項目(意図・影響範囲・運用影響)と変革ふりかえりへの回答が必須
- [ ] 承認と同時にスコープ台帳(In/Out)の登録が完了していることが通過条件になる
- [ ] 通過時に「AI ツールのコンテキストをリセットする」リマインドが表示される

### US-05 警告型ゲートの通過とリスク引き継ぎ(G2 等) 〔課題E〕
**ファシリテータ**として、警告型ゲートは未完了項目があっても通過させたい。ただし未完了項目はリスクとして可視化され続けてほしい。柔軟さと統制を両立するため。

- [ ] 未完了項目があっても進行できる
- [ ] 未完了のまま通過した項目は「引き継いだリスク」としてダッシュボードに表示され続ける
- [ ] 通過の操作と未完了項目は監査証跡に記録される

### US-06 変革ふりかえり 〔課題J〕
**ゲート承認者**として、承認時に旧習慣回帰チェックに回答したい。チームが AI ネイティブな視座を保てているかを節目で確認するため。

- [ ] ★承認必須ゲートの承認時に回帰チェック項目(人間が成果物を直接書いていないか等)が表示される
- [ ] 「回帰あり」の回答は監査証跡とファシリテータの全体進捗ボードに表示される

## トレーサビリティ(ゴール乖離の防止)

### US-07 顧客課題ツリーの可視化 〔課題B〕
**PM**として、顧客課題→ユーザーストーリー→Unit のツリーと、どこにも紐付かない孤児を見たい。当初ゴールからの乖離の兆候を早期発見するため。

- [ ] PRFAQ の顧客課題を頂点にしたツリーが表示される(機能追加要望は顧客課題の直下)
- [ ] 未紐付け、または Out スコープ・削除済み課題に紐付いた項目がハイライトされる
- [ ] 各ノードから成果物リンクへ遷移できる

### US-08 スコープ台帳 〔課題B〕
**PM**として、PRFAQ 確定時に In/Out を明示登録したい。Out にした機能が後で復活する場合は承認と理由を必須にしたい。暗黙のスコープ拡大を防ぐため。

- [ ] In/Out を項目単位で登録できる(G1 の通過条件)
- [ ] Out 項目と同名・類似の機能追加要望に「Out 済み」表示が付く
- [ ] Out 項目の復活にはビジネスオーナー承認+理由記録が必須

### US-09 機能追加のトレーサビリティゲート(G4) 〔課題B〕
**PM**として、MVP レビュー後の機能追加要望を顧客課題に紐付けた上で承認したい。紐付けられない要望は承認できないようにしたい。機能膨張と PRFAQ 乖離を構造的に防ぐため。

- [ ] 機能追加要望は作成時は紐付けなしで登録できる(敷居を上げない)
- [ ] 顧客課題に紐付いていない要望は G4 承認操作ができない
- [ ] 承認・却下の判断と理由が監査証跡に記録される

### US-10 クローズドクエスチョン・レビューシート生成 〔課題B〕
**PM**として、MVP ユーザーレビュー用にストーリーごとのクローズドクエスチョン形式レビューシートを生成したい。レビューがオープンクエスチョン化して要望が発散するのを防ぐため。

- [ ] ストーリー一覧から「この画面で○○できましたか(はい/いいえ/条件付き)」形式の markdown を生成・エクスポートできる
- [ ] シートには自由記述欄より先に選択式設問が並ぶ

## Unit と I/F 契約(統合の破綻防止)

### US-11 Unit 難易度アセスメント 〔課題D〕
**アーキテクト**として、各 Unit をチェックリスト形式で難易度評価したい。高難易度 Unit には統合の定石ガイドを得たい。開発難易度の差による統合破綻を予防するため。

- [ ] チーム経験・技術新規性・外部依存の観点で評価を記録できる
- [ ] 高難易度判定の Unit に定石ガイド(契約のモック先行固定など)が表示される

### US-12 I/F 契約の登録と確定ゲート(G3) 〔課題D〕
**アーキテクト**として、Unit 間の I/F 契約(OpenAPI/PACT リンク)を登録し、全 Unit 代表の承認で確定したい。契約確定を Construction の開始条件にするため。

- [ ] Unit 間契約を当事者 Unit・契約ドキュメントリンク付きで登録できる
- [ ] コンテキストマップ(Mermaid)を登録・表示できる
- [ ] アーキテクトと全 Unit 代表の承認が揃うまで G3 を通過できない
- [ ] Unit 代表が未指定の Unit はアーキテクトが承認を代行する

### US-13 契約変更要求フロー 〔課題D〕
**Unit 開発者**として、開発中に契約変更が必要になったら変更要求を起票し、影響 Unit の代表の承認を経て確定したい。無断の契約変更による統合破綻を防ぐため。

- [ ] 起票すると契約の当事者 Unit が影響先として自動リストアップされる
- [ ] 影響 Unit 代表全員の承認が揃うまで契約は「変更要求中」のまま確定しない
- [ ] 承認を経ない契約ステータスの直接変更はできない

## 日々の進行(ボトルネックの解消)

### US-14 ロール別「今やること」 〔課題E〕
**メンバー**として、ログインしたら自分が今やるべきこと(承認待ち・回答待ち・未完了チェック)を最上部で見たい。自分がボトルネックになっていることに気づくため。

- [ ] 自分宛ての承認待ちゲート・回答待ち質問ファイル・未完了チェックリストが一覧される
- [ ] 自分の対応を待っている他メンバー(ブロックしている相手)が表示される

### US-15 エスカレーション案内 〔課題E〕
**メンバー**として、詰まったときに「誰に・何を・どう聞くか」の案内が欲しい。ビジネス層と開発者層のコミュニケーション断絶で停滞しないため。

- [ ] 現在のステージに応じた「詰まりの種類→相談先ロール→聞き方テンプレート」が表示される
- [ ] 相談先ロールに該当するプロジェクトメンバー名が表示される

### US-16 Vibe Code 警告と逆方向伝播 〔課題G〕
**Unit 開発者**として、上流の設計を「要更新」にせず完了済みコードステージを再オープンしようとしたら、警告と逆方向伝播チェックを受けたい。設計と実装の乖離を防ぐため。

- [ ] 上流が完了状態のまま下流を再オープンすると警告が表示される
- [ ] 逆方向伝播チェックリスト(要件・ストーリーへの影響確認)への回答が求められる
- [ ] 上流が「要更新」になると依存する下流ステージに「上流変更あり」バッジが付く

### US-17 全体進捗ボード 〔課題E・J〕
**ファシリテータ**として、フェーズ×Unit の進捗マトリクス・滞留日数・回帰シグナルを一目で見たい。詰まりと旧習慣回帰を早期に発見してテーラリングに反映するため。

- [ ] フェーズ×Unit のステージ状態と滞留日数が表示される
- [ ] 変革ふりかえりの「回帰あり」回答が集計表示される

### US-18 監査証跡 〔課題I〕
**ファシリテータ**として、全ゲート通過・承認・スキップ・契約変更・スコープ変更の証跡を時系列で見てエクスポートしたい。組織の監査・文書化プロセスを開発速度に追従させるため。

- [ ] すべての状態変更が実行者・タイムスタンプ付きで自動記録される
- [ ] 種別・期間でフィルタし、markdown でエクスポートできる

### US-19 プロセステンプレートのテーラリング 〔課題A・C・J〕
**ファシリテータ**として、チェックリスト・プロンプト・変革視座・エスカレーション案内を YAML で編集し、次のプロジェクトから反映したい。組織の知見を属人化させずプロセス定義として資産化するため。

- [ ] YAML の変更が新規プロジェクトに反映される(進行中プロジェクトには影響しない)
- [ ] 不正な YAML は起動時にバリデーションエラーとして明示される
