# BizDevX Accord 設計ドキュメント(spec)

- 作成日: 2026-07-04
- ステータス: レビュー中
- 対象: BizDevX Accord — ビジネス企画から開発までの変革に伴走するプロセスナビゲーター Web アプリ(MVP)
- リポジトリ: https://github.com/ikeom-je/bizdevx-accord

## 1. 目的と背景

### 1.0 プロジェクトビジョンと名前の由来

**BizDevX Accord**(Business & DLC transformation accord)は、サービス企画(AWS の Digital Innovation Program に相当する Working Backwards 型の構想)から開発ライフサイクル(AI-DLC)までの変革に、**手段に囚われず本質から伴走する AI ツールとその AI Agent** を目指すプロジェクトである。

- **bizdevx** = ビジネスと開発の変革。特定手法(DI や AI-DLC)ではなく「手段ではなく本質の改革」を名前にする思想
- **accord** = 調和・伴走。プロセスを強制する管理ツールではなく、チームに伴走し調和させる存在

**BPR(思想・文化・視座の変革)はこのプロジェクトの中核である。** DI と AI-DLC の実践には、根本的な思想・文化・視座から変えて AI ベースのフローに再設計すること(BPR)が必要である。したがって本ツールは「これまでのワークフローを単に AI で高速化するための伴走作業とそのツール」には**しない**。目指すのは次の視座転換への伴走である:

| 従来の視座 | AI ネイティブな視座(本ツールが定着させるもの) |
|-----------|-----------------------------------------|
| 人間が成果物を作り、AI が補助する | AI が成果物を作り、人間は意図の提示・判断・監督に集中する |
| 網羅的な要件・機能を積み上げる | 顧客価値(PRFAQ)を起点に、削ぎ落として最小価値に集中する |
| 技術・体制の制約から発想する | 技術的決定を後ろ倒しし、本質的複雑性にフォーカスする |
| 口頭・会議で決めて記憶に頼る | 質問と決定をファイルに構造化し、文書で意思決定する |
| プロセス遵守が目的化する | プロセス自体を Context に応じてテーラリングし続ける |

長期ビジョンには伴走 AI Agent を含むが、**本 spec が対象とする MVP は LLM を組み込まないプロセスナビゲーター**である(1.2 参照)。ただし上記の視座転換を促す仕掛け — **チーム憲章・変革視座・変革ふりかえり・モブセッション記録と分業化シグナル**(4章) — は MVP から組み込む。プロセス定義をデータとして持つハイブリッド構造(2章)により、将来のプロセス拡張と AI Agent の追加を可能にしておく。

### 1.1 MVP の目的

Digital Innovation(Working Backwards によるサービス構想)と AI-DLC(AI 駆動開発ライフサイクル)を組み合わせたプロセス(以下 **bizdevx 標準プロセス**)の進行を、参加者の知見レベルに依存せず一定品質で回すための**プロセスナビゲーター Web アプリ**を作る。

一言で言うと「**今どのステージにいて、誰が何を決めるべきで、次に進む条件は何か**」を管理・指南するアプリである。

### 1.2 スコープ外(重要な設計判断)

- **LLM は組み込まない(プロセスナビ型)**。AI 作業は利用者の手元ツール(Claude Code / Kiro 等)で実施する。アプリはそのためのカスタマイズ済みプロンプトを配布する。
- **成果物の実体は管理しない(リンク+ステータス管理)**。PRFAQ・ユーザーストーリー・Unit 定義・I/F 契約などの実体は git リポジトリや既存ドキュメント管理に置き、アプリは各成果物への URL リンクとステータスのみを保持する。

### 1.3 解決する課題(統合課題マップ)

利用者から提示された4課題(A〜D)、公開情報から確認した AI-DLC 実践上の課題(E〜I)、および利用者フィードバックによる変革課題(J・K)を統合する。

| # | 課題 | 出所 |
|---|------|------|
| A | サービスゴール(PRFAQ)の品質が経営状況や PM の知見レベルに依存する | 利用者課題1 |
| B | MVP 後のユーザーレビューがオープンクエスチョン化し、機能が増えて当初の PRFAQ から乖離・複雑化する | 利用者課題2 |
| C | ドメイン分割・機能集約・技術選定といった上流設計が開発者の知見レベルでぶれる | 利用者課題3 |
| D | コンポーネント統合のインターフェース合わせが、コンポーネント開発難易度の差で実現できないことがある | 利用者課題4 |
| E | AI の生成速度に人間のレビュー・合意形成・承認が追従できずボトルネック化する | 公開情報 |
| F | 「動くか」の表面確認だけで受け入れ、意図・影響範囲・運用影響を理解しないまま出荷する | 公開情報 |
| G | 設計ドキュメントを迂回した直接コード編集(Vibe Code)で設計と実装が乖離する | 公開情報(awslabs/aidlc-workflows) |
| H | 暗黙知・既存制約・依存関係が AI に渡らず、もっともらしいが危険な提案が採用される | 公開情報 |
| I | 承認・文書化・監査の組織プロセスが AI-DLC の速度に追従できない | 公開情報 |
| J | ツールとプロセスを導入しても思想・文化・視座が旧来のまま(AI を従来フローの高速化にしか使わない)で、旧習慣に回帰する | 利用者フィードバック |
| K | フェーズごとにロールが分業・断絶する: 企画(目的・スコープ・KGI/KPI)は経営・ビジネスサイドだけ、設計・開発は開発者だけで進み、相互の知見が入らない | 利用者フィードバック |

課題 K への基本方針は **Mobbing(モブワーク)** である。AI-DLC の実践知見(公開情報)でも、AI の生成速度を活かすにはステークホルダー全員が同席して AI への指示・レビュー・意思決定を同期的に行うモブが本質とされる。本アプリはロール別の分業画面を提供しつつ、重要ステージをモブとして定義・記録・監視する仕掛け(4.4)で分業への固着を防ぐ。

参考一次情報: [awslabs/aidlc-workflows](https://github.com/awslabs/aidlc-workflows)(「Always in Control」原則、質問ファイル→ドキュメント→承認の3段階、`aidlc-state.md`/`audit.md`、ゲートでのコンテキストリセット、設計更新→コード再生成の規律)。

## 2. アーキテクチャ方針(ハイブリッド型)

**プロセス定義は設定データ、課題直撃の画面は専用実装**とする。

- プロセス定義(ステージ構成・チェックリスト・ゲート条件・ロール・プロンプト集・深さプロファイル・エスカレーション案内)は **git 管理された YAML** として持つ。ファシリテータはコード変更なしにテーラリングできる。これにより属人知見をプロセス定義として資産化する(課題 A・C の中核対策)。
- 課題直撃の3画面 — **トレーサビリティ台帳(課題B)**、**I/F 契約ボード(課題D)**、**ロール別ダッシュボード(課題E)** — は専用実装し、UX を妥協しない。
- その他のステージ画面は、YAML 定義から共通レイアウトでレンダリングする汎用画面(ステージナビ)とする。

案比較: 完全汎用ワークフローエンジン型は MVP まで遠く専用 UX が作りにくい。完全ハードコード型はテーラリング思想(AI-DLC の真価はプロジェクト Context に応じたテーラリング)と相性が悪い。よってハイブリッドを採用する。

## 3. ロール設計

| ロール | 責務 | 主な画面 |
|--------|------|---------|
| ビジネスオーナー | PRFAQ 承認、スコープ変更承認 | ダッシュボード(承認待ちキュー+ゴール乖離サマリ) |
| プロダクトマネージャー(PM) | PRFAQ 作成主導、ストーリー・機能追加の紐付け管理 | トレーサビリティ台帳+ステージナビ |
| ファシリテータ | プロセス全体の健全性監視、プロセス定義のテーラリング | ダッシュボード(全体進捗ボード)+プロセス定義(YAML)管理 |
| アーキテクト/リード | Unit 分割、I/F 契約、技術選定(ADR) | 契約ボード+ステージナビ(技術選定) |
| Unit 開発者 | 担当 Unit の Construction 実施 | Unit 別ステージナビ+契約ボード(参照) |

- 「ゴール乖離サマリ」「全体進捗ボード」は独立画面ではなく、5.1 ロール別ダッシュボードのロール別セクションである。
- **ADR は専用画面・専用エンティティを持たない**。技術選定ステージの ArtifactLink(種別: ADR)として登録し、ステージナビ内に一覧表示する。

- **主導と参加(モブ前提)**: ステージの担当ロールは「主導(lead)」であり、そのロールの占有ではない。各ステージは主導ロールに加えて**必須参加ロール**と**実施形態(mob / solo)**を持つ(4.1)。mob 指定のステージは、全参加ロールが同席して AI への指示・レビュー・意思決定を同期的に行うことを前提とする。標準テンプレートでは、企画(Phase 0: ペルソナ・注力課題・PRFAQ・KGI/KPI・スコープ)に**開発者を含む全ロール**が、Construction のドメインモデリングや MVP レビューに **PM・ビジネスオーナー**が参加する(4.2)。
- 1ユーザーが複数ロールを兼ねられる(小規模チーム対応)。
- **Unit 代表**: 各 Unit にはメンバーを割り当て、うち1名を「Unit 代表」に指定する(データモデルの UnitAssignment)。代表未指定の Unit の承認はアーキテクト/リードが代行する。G3 や契約変更の承認者はこのルールで機械的に決まる。
- **エスカレーション案内**: 各ステージ・チェック項目に「詰まりの種類 → 相談先ロール → 聞き方テンプレート」を YAML で紐付ける。ビジネス層⇔開発者層のコミュニケーションが必要な場面を明示する(課題E)。

## 4. プロセスモデル

### 4.1 プロセステンプレート(YAML)

- ステージ定義: id、名前、フェーズ、**主導ロール**、**必須参加ロール**、**実施形態(mob / solo)**、目的文、**変革視座**(このステージが従来のやり方とどう違うか・捨てるべき旧習慣。4.4 参照)、コンテキスト準備チェック、完了チェックリスト(良/悪例つき)、プロンプト集(目的・修正観点つき)、エスカレーション案内、順序依存(上流ステージ)
- ゲート定義: id、対象ステージ、種別(★承認必須 / ⚠警告型)、承認ロール、通過条件、旧習慣回帰チェック項目(4.4 の変革ふりかえり用)
- 深さプロファイル: `poc` / `new-service` / `brownfield` の3種。プロファイルによりステージの有無・チェックリストの厚さを切り替える(公開情報の「課題の複雑さに応じた深さで回す」実務知見を反映)
- テンプレートはバージョンを持ち、プロジェクトは開始時にテンプレートバージョンを**固定**する(進行中プロジェクトがテンプレート改善で壊れない)

### 4.2 bizdevx 標準テンプレート(new-service プロファイル)の流れ

```
Phase 0: DI (Working Backwards)  《mob: 開発者を含む全ロール参加》
  チーム憲章(AI ネイティブな働き方への合意。4.4 参照)
  → ペルソナ深掘り → 注力課題選定
  → PRFAQ 作成+成功指標(KGI/KPI)+スコープ台帳(In/Out)
  ── [G1] PRFAQ 確定ゲート ★承認必須(ビジネスオーナー) ──
Phase 1: Inception  《mob: architect 主導+PM・ビジネスオーナー参加》
  ユーザーストーリー → 画面モック → Unit of Work
  ── [G2] Unit 分割承認 ⚠警告型 ──
  → コンテキストマップ → Unit 難易度アセスメント → I/F 契約(OpenAPI/PACT)
  ── [G3] I/F 契約確定ゲート ★承認必須(アーキテクト+全 Unit 代表) ──
Phase 2: Construction (Unit 単位で並列)
  ドメインモデリング《mob: unit_dev 主導+PM 参加(用語・業務ルールを即決)》
  → コード → テスト → アーキテクチャ追加
  各ステージ: コンテキスト準備チェック+完了チェックリスト(⚠警告型)
  契約変更が必要になったら → 契約ボードで変更要求(★影響 Unit 代表の承認必須)
Phase 3: 統合・MVP レビュー  《mob: PM 主導+開発者・ビジネスオーナー参加》
  QA/受け入れ → ユーザーレビュー(クローズドクエスチョン形式)
  → 機能追加要望 ── [G4] トレーサビリティゲート ★PRFAQ 顧客課題への紐付け必須+PM 承認 ──
  → 追加分は Phase 1 に戻って次サイクルへ
```

- 《mob: …》はステージ定義の実施形態と主導/必須参加ロールの標準値を示す。テーラリング可能。
- **成功指標(KGI/KPI)**は独立ステージではなく PRFAQ 作成ステージの成果物リンク+完了チェックリスト(「KGI/KPI を定義し測定方法を決めたか」「開発者を含むモブで合意したか」)として扱い、G1 の承認対象に含まれる。経営・ビジネスサイドだけでなく開発者もモブ参加者として KGI/KPI の構想に加わる(課題K)。

### 4.3 ゲート共通仕様

- **★承認必須ゲート**: チェックリスト完了+指定ロール全員の承認で通過。承認時に「理解確認」3項目(このゲートの成果物の**意図・影響範囲・運用影響**を自分の言葉で説明できるか)への自己申告チェック(課題F)と、**変革ふりかえり**(旧習慣回帰チェック。4.4 参照/課題J)への回答を必須とする。
- **⚠警告型ゲート**: 未完了でも進行可能。ただし未完了項目は「引き継いだリスク」として以降ダッシュボードに表示され続ける(消えない)。
- ゲート通過・承認・スキップ・差し戻しはすべて監査証跡に自動記録される(課題I)。
- ゲート通過時に「ここで AI ツール側のコンテキストをリセットせよ」というリマインドを表示する(awslabs 実践知見: ゲートはコンテキストリセットの最適な分岐点)。

### 4.4 変革の仕掛け(BPR / 課題J)

「従来ワークフローの AI 高速化」への回帰を防ぐため、プロセスの4箇所に視座転換の仕掛けを埋め込む。いずれもプロセステンプレート(YAML)で定義され、テーラリング可能。

1. **チーム憲章(Phase 0 冒頭のステージ)**: プロジェクト開始時に、1.0 の視座転換表をベースにした AI ネイティブな働き方の合意項目(例:「人間は成果物を書かず、意図の提示とレビューに集中する」「決定は口頭でなく質問ファイルで行う」「AI の出力は削ぎ落とす方向でレビューする」)をチーム全員が確認・合意する。合意記録は憲章として全画面のヘッダーから常時参照できる。
2. **変革視座(全ステージ共通)**: 各ステージの冒頭に「このステージは従来のやり方とどう違うか」「捨てるべき旧習慣」を表示する(例: ユーザーストーリー計画では「非機能要件・見積もり・技術スタックを今決めたくなるのが旧習慣。価値だけに集中する」)。手順のガイドではなく視座のガイドである。
3. **変革ふりかえり(★承認必須ゲートの通過時)**: ゲート承認者は理解確認3項目に加え、旧習慣回帰チェック(例:「人間が成果物を直接書き始めていないか」「口頭決定でファイル化を省略していないか」「AI の生成物を無批判に受け入れていないか」「**ロール分業・引き継ぎ駆動に戻っていないか(モブを省略していないか)**」)に回答する。「回帰あり」の回答は監査証跡とファシリテータの全体進捗ボードに表示され、テーラリングの入力になる。
4. **モブセッション記録と分業化シグナル(課題K)**: mob 指定ステージでは、ステージナビからモブセッション(参加メンバー・日時・決定メモ)を記録する。アプリは参加記録とチェックリスト・承認の実行者から**ロール構成を機械的に算出**し、(a) 必須参加ロールを欠いたまま完了した mob ステージ、(b) 単一ロールのみで作業が完結し続けているフェーズ、を**分業化シグナル**としてファシリテータの全体進捗ボードに表示する(LLM 不要のルールベース検出)。チーム憲章の合意項目には「企画に開発者が、開発にビジネスが参加する(重要な意思決定はモブで行う)」を含める。

### 4.5 Vibe Code 抑止(ステージ順序制御)

- **StageInstance の状態遷移**: `未着手 → 進行中 → 完了`。`完了 → 要更新` は (a) 上流ステージが要更新になった場合の自動伝播、または (b) 手動差し戻し で発生する。`要更新 → 進行中` が再オープンである。
- ステージは順序依存(上流→下流)を持つ。
- 上流成果物(設計)のステータスを「要更新」に戻さずに、完了済みの下流ステージ(コード)を再オープンしようとすると、警告+**逆方向伝播チェックリスト**(「この変更は要件・ユーザーストーリーに影響するか?」)を提示する(課題G)。
- 上流ステージが「要更新」になると、依存する下流ステージに「上流変更あり」バッジが付く。

## 5. 画面構成

### 5.0 ナビゲーション構造(画面間導線)

- **グローバルヘッダー(プロジェクト内全画面共通)**: ダッシュボード / トレーサビリティ台帳 / 契約ボード / 監査証跡 への固定リンク+チーム憲章の常設リンク(4.4-1)。
- **プロセスマップ(全ロール共通のステージ一覧・ダッシュボード内)**: フェーズ順にステージを一覧表示する。プロジェクト共通ステージに加え、**自分が割り当てられた Unit の Construction 系 StageInstance** を含み、各行はステータスバッジ+直後のゲート状況つき。クリックでステージナビ(5.4)へ遷移する。これが「次のステージを開始する」という日常業務の入口となる(ファシリテータの全体進捗ボードは全 Unit 横断の監視用マトリクスであるのに対し、プロセスマップは自分に関係する範囲の作業用一覧)。
- ステージナビ・台帳・契約ボードの各項目からは、関連する成果物リンク・ゲート・Unit へ相互リンクする。

### 5.1 ロール別ダッシュボード(ホーム)〔専用実装/課題E・F〕

- **プロセスマップ**: 全ロール共通のステージ一覧(5.0 参照)。日常業務でステージへ入る導線
- **あなたの番です**: 回答待ちの質問ファイル(リンク)、承認待ちゲート、担当ステージの未完了チェックリスト
- **引き継いだリスク**: 警告型ゲートを未完了のまま通過した項目の一覧
- **ブロックされている人**: 自分の承認・回答を待っている他メンバーの表示(レビュー渋滞の可視化)
- **困ったら**: 現在ステージのエスカレーション案内
- **ロール別セクション**: ビジネスオーナーには「ゴール乖離サマリ」(孤児件数・Out スコープ再登場件数・承認待ちスコープ変更の要約)、ファシリテータには「全体進捗ボード」(フェーズ×Unit のステージ進捗マトリクス・滞留日数・変革ふりかえりの回帰シグナル集計・**分業化シグナル**(4.4))を追加表示する

### 5.2 トレーサビリティ台帳〔専用実装/課題B の中核〕

- PRFAQ を頂点としたツリー表示: **顧客課題 → ユーザーストーリー → Unit**。**機能追加要望は紐付いた顧客課題の直下に表示**する(Unit の子ではない)。各ノードは成果物リンク+ステータスを持つ。
- **紐付けルール**: 顧客課題への紐付けは**作成時は任意**(登録の敷居を上げない)。ただしストーリーは未紐付けのままだと孤児として警告され続け、機能追加要望(ChangeRequest)は **G4 承認時に紐付けが必須**(未紐付けでは承認操作ができない)。
- **孤児検出**: どの顧客課題にも紐付かない、または Out スコープ・削除済みの課題に紐付いたストーリー・機能追加要望を自動ハイライト(乖離の兆候)。
- **スコープ台帳**: PRFAQ 確定時に In/Out を明示登録する。Out 項目が機能追加要望として再登場したら「Out 済み」と表示し、復活にはビジネスオーナー承認+理由記録を要求する。再登場の検出は**名称の完全一致による自動サジェスト+PM による手動リンク**で行う(MVP に LLM はないため類似判定はしない)。
- **クローズドクエスチョン・レビューシート生成**: MVP ユーザーレビュー用に、ストーリーごとの「この画面で○○できましたか(はい/いいえ/条件付き)」形式のレビューシート(markdown)を生成・エクスポートする。オープンクエスチョン化を構造的に防ぐ。

### 5.3 I/F 契約ボード〔専用実装/課題D の中核〕

- Unit 間契約の一覧: 契約名、当事者 Unit、契約ドキュメント(OpenAPI/PACT)リンク、ステータス(draft / 確定 / 変更要求中)。
- コンテキストマップ(Mermaid テキスト)を登録・レンダリング表示。
- **契約変更要求フロー**: 起票 → 契約の当事者 Unit を影響先として自動リストアップ → 各 Unit 代表の承認 → 確定。承認を経ない契約ステータス変更はできない。
- **Unit 難易度アセスメント**: Inception 時に各 Unit をチェックリスト形式で評価(チーム経験・技術新規性・外部依存)。高難易度 Unit には定石ガイド(「契約をモック/スタブで先に固定し他 Unit を先行させる」等)を提示する。

### 5.4 ステージナビ〔汎用実装/課題A・C・G・H〕

YAML 定義から共通レイアウトでレンダリング:

1. このステージの目的(1段落)+**変革視座**(従来との違い・捨てるべき旧習慣)〔課題J〕+**主導ロール・必須参加ロール**(mob 指定なら「モブで実施」バナー)〔課題K〕
1b. mob 指定ステージには**モブセッション記録**(参加メンバー選択・日時・決定メモ)。必須参加ロールが揃っていない記録には警告表示〔課題K〕
2. コンテキスト準備チェック(ビジョン doc・技術環境 doc・既存制約は用意したか)〔課題H〕
3. プロンプト集(「このプロンプトの目的」「修正するときの観点」付き、コピーボタン)
4. 完了チェックリスト(良/悪例つき。例: PRFAQ「顧客課題を一文で言えるか」、ストーリー「20 個を超えていないか」)
5. 成果物リンク登録+ステータス変更
6. 上流成果物が「要更新」の場合の警告+逆方向伝播チェック〔課題G〕

### 5.5 監査証跡ビュー〔課題I〕

全ゲート通過・承認・スキップ・契約変更・スコープ変更をタイムスタンプ+実行者付きで時系列表示。フィルタと markdown エクスポートのみ。

※ プロセス定義の GUI 編集画面は MVP では作らない。YAML を git で直接編集し、アプリが再読み込みする。

## 6. データモデル(主要エンティティ)

```
ProcessTemplate(YAML 読込, version)
Project(name, depthProfile, templateVersion 固定)
Member(project, user, roles[])
Unit(project, name, difficultyAssessment)
UnitAssignment(unit, member, isRepresentative)  ※代表は Unit ごとに1名
StageInstance(project または unit, stageDefId, status: 未着手/進行中/完了/要更新, statusChangedAt)
  ※statusChangedAt はダッシュボードの滞留日数算出に使う
ChecklistResult(stageInstance, itemId, checked, by, at, skipReason?)
※(stageInstance, itemId)に対し複数行を許す(チーム憲章のようにメンバーごとの合意を記録する項目があるため)
ArtifactLink(stageInstance, kind: artifact/question, name, url, status)
  ※質問ファイルは kind=question(status: 回答待ち/回答済み)として表現し、5.1「あなたの番です」の供給元になる
MobSession(stageInstance, participantMemberIds[], heldAt, note?)  ※課題K: モブ実施の記録
GateApproval(gateId, approver, understandingCheck{意図/影響範囲/運用影響},
             regressionCheck{旧習慣回帰の有無+回帰項目}, decision, at)
※チーム憲章は専用エンティティを持たない。Phase 0 冒頭ステージの ChecklistResult として合意を記録する
-- トレーサビリティ --
CustomerProblem(project, PRFAQ 由来, text, artifactLink)
Story(project, text, customerProblemId?, units[] 多対多)  ※未紐付けは孤児として警告
ChangeRequest(project, text, customerProblemId?, scopeEntryId?, status, approvals)
  ※G4 承認時に customerProblemId 必須。scopeEntryId は「Out 済み」表示のためのスコープ台帳項目への手動リンク(PM が確定。5.2)
ScopeEntry(project, feature, inOut, decidedAt, reason,
           resurrectedAt?, resurrectedBy?, resurrectReason?)  ※Out→In 復活の承認記録(US-08。復活時に inOut を in へ更新し3項目を記録)
-- 契約 --
Contract(unitA, unitB, name, url, status: draft/確定/変更要求中)  ※MVP は2者間契約のみ(意図的な制約)
ContractChangeRequest(contract, description, impactedUnits[], approvals, status)
-- 横断 --
AuditLog(project, event, actor, at, detail)  ※全状態変更から自動生成
```

設計原則: **プロセス定義(テンプレート)と実行状態(インスタンス)を分離**する。

## 7. MVP スコープ

**含む**: プロジェクト作成(深さプロファイル選択)/ ステージナビ(変革視座・主導/必須参加ロール表示含む)/ **変革の仕掛け**(チーム憲章・変革ふりかえり・**モブセッション記録・分業化シグナル**)/ **GAP 分析プロンプト**(テンプレート同梱。12章 段階1)/ G1・G3・G4 承認必須ゲート / G2 を含む警告型ゲート・チェック / トレーサビリティ台帳(孤児検出・スコープ台帳・レビューシート生成含む)/ 契約ボード(変更要求フロー・難易度アセスメント含む)/ ロール別ダッシュボード / 監査証跡 / bizdevx 標準テンプレート YAML 1本(3プロファイル)

**含まない(将来)**: プロセス定義 GUI 編集 / Slack・メール通知 / SSO / 複数プロセステンプレート / Operations フェーズ / レビューシート回答の集計分析 / **MCP サーバー化**(12章 段階2)/ **伴走 AI Agent**(LLM による成果物品質チェック・ゴール乖離検知・次アクション提案・詰まり検知時の能動的な仲介。12章 段階3)

※ BPR は将来機能ではなく、MVP のプロセステンプレートと変革の仕掛け(4.4)に思想として埋め込まれている。

## 8. 技術構成

- 単一 Web アプリ+**SQLite**。ローカル/社内ネットワークで動くシンプル構成。
- 認証は MVP ではプロジェクトメンバー選択式(社内ネットワーク前提。SSO は将来)。
- ゲート通過判定・トレーサビリティ整合性(孤児検出)・契約変更の影響 Unit 算出・ステージ順序制御を**ピュアなドメインロジック**として Web/DB から分離して実装する(AI-DLC の「本質的複雑性へのフォーカス」に従う。このアプリ自体を AI-DLC で開発するデモにもなる)。
- フレームワーク等の具体選定は実装計画時に決定する(技術的決定の後ろ倒し)。

## 9. エラーハンドリング

- YAML テンプレートは読込時にスキーマバリデーションし、不正定義は起動時に明示エラーで止める(黙って壊れない)。
- 承認の同時競合は楽観ロックで後勝ちを拒否する。
- 成果物リンクは URL 形式のみ検証(到達性チェックはしない)。

## 10. テスト戦略

- ドメインロジック(ゲート通過判定、孤児検出、契約変更の影響 Unit 算出、要更新の下流伝播、警告型リスクの引き継ぎ、回帰シグナルの集計、分業化シグナルの算出)を**ユニットテストで網羅**する。
- 画面は主要フロー(PRFAQ 確定 → Inception 進行 → 契約確定 → 機能追加ゲート)の E2E を最小限。
- テンプレート YAML のスキーマバリデーションのテスト(正常系・異常系)。

## 12. ロードマップ: 構想→設計→開発の GAP を Agent との対話で可視化する

「企画した構想が設計・開発でどこまでぶれなく実現できているか」の可視化は、次の3段階で実現する。役割分担の原則は「**アプリ=プロセス状態と統制の真実の源 / Agent=成果物の意味を分析する者**」であり、アプリ本体に LLM を組み込まない判断(1.2)は全段階で維持する。

| 段階 | 内容 | GAP 検出の性質 | スコープ |
|------|------|--------------|---------|
| 1. 構造的 GAP + プロンプト連携 | 孤児検出・スコープ台帳・要更新伝播・各種シグナル(機械検出)に加え、**GAP 分析プロンプト**をテンプレートに同梱。プロジェクト状態の要約と成果物リンク一覧を手元の Agent(Claude Code 等)に渡し、「顧客課題ごとに設計・実装の対応と不足を挙げよ」等の意味的 GAP 分析を対話で行う | 構造=自動 / 意味=手元 Agent(手動起動) | **MVP(本 spec)** |
| 2. MCP サーバー化 | アプリのプロセス状態を MCP ツールとして公開し、手元の Agent が**常時対話**で GAP 分析できるようにする。分析結果(発見した GAP)は書き込みツール経由でアプリに還流し、監査証跡・ダッシュボードに乗る | 構造=自動 / 意味=手元 Agent(常時・双方向) | MVP 後の次フェーズ |
| 3. 伴走 AI Agent | アプリ内組込み Agent が能動的にゴール乖離を検知し、次アクションを提案・詰まりを仲介する(7章 将来スコープ) | 構造・意味とも能動検知 | 将来 |

段階2の MCP ツール案:

- 読み取り: `get_project_state`(フェーズ・ステージ・ゲート状況)/ `get_traceability_tree`(孤児含む)/ `get_signals`(引き継いだリスク・回帰・分業化)/ `list_artifact_links`(成果物リンク一覧)/ `get_audit_log`
- 書き込み(すべて監査記録を通す): `create_change_request`(発見した GAP を機能追加要望として起票)/ `create_question_link`(質問ファイルリンク登録)/ `request_needs_update`(上流成果物の差し戻し起票)

段階2のツール群は段階3の組込み Agent の実行基盤としてそのまま再利用する。
