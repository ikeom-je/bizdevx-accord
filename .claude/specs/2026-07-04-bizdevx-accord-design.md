# BizDevX Accord 設計ドキュメント(spec)

- 作成日: 2026-07-04
- ステータス: レビュー中
- 対象: BizDevX Accord — ビジネス企画から開発までの変革に伴走するプロセスナビゲーター Web アプリ(MVP)
- リポジトリ: https://github.com/ikeom-je/bizdevx-accord

## 1. 目的と背景

### 1.0 プロジェクトビジョンと名前の由来

**BizDevX Accord**(Business & DLC transformation accord)は、サービス企画(AWS の Digital Innovation Program に相当する Working Backwards 型の構想)から開発ライフサイクル(AI-DLC)、さらに BPR(業務改革)まで、**手段に囚われず本質的な変革に伴走する AI ツールとその AI Agent** を目指すプロジェクトである。

- **bizdevx** = ビジネスと開発の変革。特定手法(DI や AI-DLC)ではなく「手段ではなく本質の改革」を名前にする思想
- **accord** = 調和・伴走。プロセスを強制する管理ツールではなく、チームに伴走し調和させる存在

長期ビジョンには伴走 AI Agent を含むが、**本 spec が対象とする MVP は LLM を組み込まないプロセスナビゲーター**である(1.2 参照)。プロセス定義をデータとして持つハイブリッド構造(2章)により、将来の BPR など別プロセスへの拡張と AI Agent の追加を可能にしておく。

### 1.1 MVP の目的

Digital Innovation(Working Backwards によるサービス構想)と AI-DLC(AI 駆動開発ライフサイクル)を組み合わせたプロセス(以下 **bizdevx 標準プロセス**)の進行を、参加者の知見レベルに依存せず一定品質で回すための**プロセスナビゲーター Web アプリ**を作る。

一言で言うと「**今どのステージにいて、誰が何を決めるべきで、次に進む条件は何か**」を管理・指南するアプリである。

### 1.2 スコープ外(重要な設計判断)

- **LLM は組み込まない(プロセスナビ型)**。AI 作業は利用者の手元ツール(Claude Code / Kiro 等)で実施する。アプリはそのためのカスタマイズ済みプロンプトを配布する。
- **成果物の実体は管理しない(リンク+ステータス管理)**。PRFAQ・ユーザーストーリー・Unit 定義・I/F 契約などの実体は git リポジトリや既存ドキュメント管理に置き、アプリは各成果物への URL リンクとステータスのみを保持する。

### 1.3 解決する課題(統合課題マップ)

利用者から提示された4課題(A〜D)と、公開情報から確認した AI-DLC 実践上の課題(E〜I)を統合する。

| # | 課題 | 出所 |
|---|------|------|
| A | サービスゴール(PRFAQ)の品質が経営状況や PM の知見レベルに依存する | 利用者課題1 |
| B | MVP 後のユーザーレビューがオープンクエスチョン化し、機能が増えて当初の PRFAQ から乖離・複雑化する | 利用者課題2 |
| C | ドメイン分割・機能集約・技術選定といった上流設計が開発者の知見レベルでぶれる | 利用者課題3 |
| D | コンポーネント統合のインターフェース合わせが、コンポーネント開発難易度の差で実現できないことがある | 利用者課題4 |
| E | AI の生成速度に人間のレビュー・合意形成・承認が追従できずボトルネック化する | 公開情報 |
| F | 「動くか」の表面確認だけで受け入れ、意図・影響範囲・運用影響を理解しないまま出荷する | 公開情報 |
| G | 設計ドキュメントを迂回した直接コード編集(Vibe Code)で設計と実装が乖離する | 公開情報(awslabs/aidlc-workflows) |
| H | 暗黙知・既存制約・依存関係が AI に渡らず、もっともらしいが危険な提案が採用される | 公開情報 |
| I | 承認・文書化・監査の組織プロセスが AI-DLC の速度に追従できない | 公開情報 |

参考一次情報: [awslabs/aidlc-workflows](https://github.com/awslabs/aidlc-workflows)(「Always in Control」原則、質問ファイル→ドキュメント→承認の3段階、`aidlc-state.md`/`audit.md`、ゲートでのコンテキストリセット、設計更新→コード再生成の規律)。

## 2. アーキテクチャ方針(ハイブリッド型)

**プロセス定義は設定データ、課題直撃の画面は専用実装**とする。

- プロセス定義(ステージ構成・チェックリスト・ゲート条件・ロール・プロンプト集・深さプロファイル・エスカレーション案内)は **git 管理された YAML** として持つ。ファシリテータはコード変更なしにテーラリングできる。これにより属人知見をプロセス定義として資産化する(課題 A・C の中核対策)。
- 課題直撃の3画面 — **トレーサビリティ台帳(課題B)**、**I/F 契約ボード(課題D)**、**ロール別ダッシュボード(課題E)** — は専用実装し、UX を妥協しない。
- その他のステージ画面は、YAML 定義から共通レイアウトでレンダリングする汎用画面(ステージナビ)とする。

案比較: 完全汎用ワークフローエンジン型は MVP まで遠く専用 UX が作りにくい。完全ハードコード型はテーラリング思想(AI-DLC の真価はプロジェクト Context に応じたテーラリング)と相性が悪い。よってハイブリッドを採用する。

## 3. ロール設計

| ロール | 責務 | 主な画面 |
|--------|------|---------|
| ビジネスオーナー | PRFAQ 承認、スコープ変更承認 | ダッシュボード(承認待ちキュー+ゴール乖離サマリ) |
| プロダクトマネージャー(PM) | PRFAQ 作成主導、ストーリー・機能追加の紐付け管理 | トレーサビリティ台帳+ステージナビ |
| ファシリテータ | プロセス全体の健全性監視、プロセス定義のテーラリング | ダッシュボード(全体進捗ボード)+プロセス定義(YAML)管理 |
| アーキテクト/リード | Unit 分割、I/F 契約、技術選定(ADR) | 契約ボード+ステージナビ(技術選定) |
| Unit 開発者 | 担当 Unit の Construction 実施 | Unit 別ステージナビ+契約ボード(参照) |

- 「ゴール乖離サマリ」「全体進捗ボード」は独立画面ではなく、5.1 ロール別ダッシュボードのロール別セクションである。
- **ADR は専用画面・専用エンティティを持たない**。技術選定ステージの ArtifactLink(種別: ADR)として登録し、ステージナビ内に一覧表示する。

- 1ユーザーが複数ロールを兼ねられる(小規模チーム対応)。
- **Unit 代表**: 各 Unit にはメンバーを割り当て、うち1名を「Unit 代表」に指定する(データモデルの UnitAssignment)。代表未指定の Unit の承認はアーキテクト/リードが代行する。G3 や契約変更の承認者はこのルールで機械的に決まる。
- **エスカレーション案内**: 各ステージ・チェック項目に「詰まりの種類 → 相談先ロール → 聞き方テンプレート」を YAML で紐付ける。ビジネス層⇔開発者層のコミュニケーションが必要な場面を明示する(課題E)。

## 4. プロセスモデル

### 4.1 プロセステンプレート(YAML)

- ステージ定義: id、名前、フェーズ、担当ロール、目的文、コンテキスト準備チェック、完了チェックリスト(良/悪例つき)、プロンプト集(目的・修正観点つき)、エスカレーション案内、順序依存(上流ステージ)
- ゲート定義: id、対象ステージ、種別(★承認必須 / ⚠警告型)、承認ロール、通過条件
- 深さプロファイル: `poc` / `new-service` / `brownfield` の3種。プロファイルによりステージの有無・チェックリストの厚さを切り替える(公開情報の「課題の複雑さに応じた深さで回す」実務知見を反映)
- テンプレートはバージョンを持ち、プロジェクトは開始時にテンプレートバージョンを**固定**する(進行中プロジェクトがテンプレート改善で壊れない)

### 4.2 bizdevx 標準テンプレート(new-service プロファイル)の流れ

```
Phase 0: DI (Working Backwards)
  ペルソナ深掘り → 注力課題選定 → PRFAQ 作成+スコープ台帳(In/Out)
  ── [G1] PRFAQ 確定ゲート ★承認必須(ビジネスオーナー) ──
Phase 1: Inception
  ユーザーストーリー → 画面モック → Unit of Work → コンテキストマップ
  → Unit 難易度アセスメント → I/F 契約(OpenAPI/PACT)
  ── [G2] Unit 分割承認 ⚠警告型 ──
  ── [G3] I/F 契約確定ゲート ★承認必須(アーキテクト+全 Unit 代表) ──
Phase 2: Construction (Unit 単位で並列)
  ドメインモデリング → コード → テスト → アーキテクチャ追加
  各ステージ: コンテキスト準備チェック+完了チェックリスト(⚠警告型)
  契約変更が必要になったら → 契約ボードで変更要求(★影響 Unit 代表の承認必須)
Phase 3: 統合・MVP レビュー
  QA/受け入れ → ユーザーレビュー(クローズドクエスチョン形式)
  → 機能追加要望 ── [G4] トレーサビリティゲート ★PRFAQ 顧客課題への紐付け必須+PM 承認 ──
  → 追加分は Phase 1 に戻って次サイクルへ
```

### 4.3 ゲート共通仕様

- **★承認必須ゲート**: チェックリスト完了+指定ロール全員の承認で通過。承認時に「理解確認」3項目(このゲートの成果物の**意図・影響範囲・運用影響**を自分の言葉で説明できるか)への自己申告チェックを必須とする(課題F)。
- **⚠警告型ゲート**: 未完了でも進行可能。ただし未完了項目は「引き継いだリスク」として以降ダッシュボードに表示され続ける(消えない)。
- ゲート通過・承認・スキップ・差し戻しはすべて監査証跡に自動記録される(課題I)。
- ゲート通過時に「ここで AI ツール側のコンテキストをリセットせよ」というリマインドを表示する(awslabs 実践知見: ゲートはコンテキストリセットの最適な分岐点)。

### 4.4 Vibe Code 抑止(ステージ順序制御)

- **StageInstance の状態遷移**: `未着手 → 進行中 → 完了`。`完了 → 要更新` は (a) 上流ステージが要更新になった場合の自動伝播、または (b) 手動差し戻し で発生する。`要更新 → 進行中` が再オープンである。
- ステージは順序依存(上流→下流)を持つ。
- 上流成果物(設計)のステータスを「要更新」に戻さずに、完了済みの下流ステージ(コード)を再オープンしようとすると、警告+**逆方向伝播チェックリスト**(「この変更は要件・ユーザーストーリーに影響するか?」)を提示する(課題G)。
- 上流ステージが「要更新」になると、依存する下流ステージに「上流変更あり」バッジが付く。

## 5. 画面構成

### 5.1 ロール別ダッシュボード(ホーム)〔専用実装/課題E・F〕

- **あなたの番です**: 回答待ちの質問ファイル(リンク)、承認待ちゲート、担当ステージの未完了チェックリスト
- **引き継いだリスク**: 警告型ゲートを未完了のまま通過した項目の一覧
- **ブロックされている人**: 自分の承認・回答を待っている他メンバーの表示(レビュー渋滞の可視化)
- **困ったら**: 現在ステージのエスカレーション案内
- **ロール別セクション**: ビジネスオーナーには「ゴール乖離サマリ」(孤児件数・Out スコープ再登場件数・承認待ちスコープ変更の要約)、ファシリテータには「全体進捗ボード」(フェーズ×Unit のステージ進捗マトリクスと滞留日数)を追加表示する

### 5.2 トレーサビリティ台帳〔専用実装/課題B の中核〕

- PRFAQ を頂点としたツリー表示: **顧客課題 → ユーザーストーリー → Unit**。**機能追加要望は紐付いた顧客課題の直下に表示**する(Unit の子ではない)。各ノードは成果物リンク+ステータスを持つ。
- **紐付けルール**: 顧客課題への紐付けは**作成時は任意**(登録の敷居を上げない)。ただしストーリーは未紐付けのままだと孤児として警告され続け、機能追加要望(ChangeRequest)は **G4 承認時に紐付けが必須**(未紐付けでは承認操作ができない)。
- **孤児検出**: どの顧客課題にも紐付かない、または Out スコープ・削除済みの課題に紐付いたストーリー・機能追加要望を自動ハイライト(乖離の兆候)。
- **スコープ台帳**: PRFAQ 確定時に In/Out を明示登録する。Out 項目が機能追加要望として再登場したら「Out 済み」と表示し、復活にはビジネスオーナー承認+理由記録を要求する。
- **クローズドクエスチョン・レビューシート生成**: MVP ユーザーレビュー用に、ストーリーごとの「この画面で○○できましたか(はい/いいえ/条件付き)」形式のレビューシート(markdown)を生成・エクスポートする。オープンクエスチョン化を構造的に防ぐ。

### 5.3 I/F 契約ボード〔専用実装/課題D の中核〕

- Unit 間契約の一覧: 契約名、当事者 Unit、契約ドキュメント(OpenAPI/PACT)リンク、ステータス(draft / 確定 / 変更要求中)。
- コンテキストマップ(Mermaid テキスト)を登録・レンダリング表示。
- **契約変更要求フロー**: 起票 → 契約の当事者 Unit を影響先として自動リストアップ → 各 Unit 代表の承認 → 確定。承認を経ない契約ステータス変更はできない。
- **Unit 難易度アセスメント**: Inception 時に各 Unit をチェックリスト形式で評価(チーム経験・技術新規性・外部依存)。高難易度 Unit には定石ガイド(「契約をモック/スタブで先に固定し他 Unit を先行させる」等)を提示する。

### 5.4 ステージナビ〔汎用実装/課題A・C・G・H〕

YAML 定義から共通レイアウトでレンダリング:

1. このステージの目的(1段落)+担当ロール
2. コンテキスト準備チェック(ビジョン doc・技術環境 doc・既存制約は用意したか)〔課題H〕
3. プロンプト集(「このプロンプトの目的」「修正するときの観点」付き、コピーボタン)
4. 完了チェックリスト(良/悪例つき。例: PRFAQ「顧客課題を一文で言えるか」、ストーリー「20 個を超えていないか」)
5. 成果物リンク登録+ステータス変更
6. 上流成果物が「要更新」の場合の警告+逆方向伝播チェック〔課題G〕

### 5.5 監査証跡ビュー〔課題I〕

全ゲート通過・承認・スキップ・契約変更・スコープ変更をタイムスタンプ+実行者付きで時系列表示。フィルタと markdown エクスポートのみ。

※ プロセス定義の GUI 編集画面は MVP では作らない。YAML を git で直接編集し、アプリが再読み込みする。

## 6. データモデル(主要エンティティ)

```
ProcessTemplate(YAML 読込, version)
Project(name, depthProfile, templateVersion 固定)
Member(project, user, roles[])
Unit(project, name, difficultyAssessment)
UnitAssignment(unit, member, isRepresentative)  ※代表は Unit ごとに1名
StageInstance(project または unit, stageDefId, status: 未着手/進行中/完了/要更新)
ChecklistResult(stageInstance, itemId, checked, by, at, skipReason?)
ArtifactLink(stageInstance, name, url, status)
GateApproval(gateId, approver, understandingCheck{意図/影響範囲/運用影響}, decision, at)
-- トレーサビリティ --
CustomerProblem(project, PRFAQ 由来, text, artifactLink)
Story(project, text, customerProblemId?, units[] 多対多)  ※未紐付けは孤児として警告
ChangeRequest(project, text, customerProblemId?, status, approvals)  ※G4 承認時に紐付け必須
ScopeEntry(project, feature, inOut, decidedAt, reason)
-- 契約 --
Contract(unitA, unitB, name, url, status: draft/確定/変更要求中)  ※MVP は2者間契約のみ(意図的な制約)
ContractChangeRequest(contract, description, impactedUnits[], approvals, status)
-- 横断 --
AuditLog(project, event, actor, at, detail)  ※全状態変更から自動生成
```

設計原則: **プロセス定義(テンプレート)と実行状態(インスタンス)を分離**する。

## 7. MVP スコープ

**含む**: プロジェクト作成(深さプロファイル選択)/ ステージナビ / G1・G3・G4 承認必須ゲート / G2 を含む警告型ゲート・チェック / トレーサビリティ台帳(孤児検出・スコープ台帳・レビューシート生成含む)/ 契約ボード(変更要求フロー・難易度アセスメント含む)/ ロール別ダッシュボード / 監査証跡 / bizdevx 標準テンプレート YAML 1本(3プロファイル)

**含まない(将来)**: プロセス定義 GUI 編集 / Slack・メール通知 / SSO / 複数プロセステンプレート(**BPR 用テンプレート**を含む)/ Operations フェーズ / レビューシート回答の集計分析 / **伴走 AI Agent**(LLM による成果物品質チェック・ゴール乖離検知・次アクション提案・詰まり検知時の能動的な仲介)

## 8. 技術構成

- 単一 Web アプリ+**SQLite**。ローカル/社内ネットワークで動くシンプル構成。
- 認証は MVP ではプロジェクトメンバー選択式(社内ネットワーク前提。SSO は将来)。
- ゲート通過判定・トレーサビリティ整合性(孤児検出)・契約変更の影響 Unit 算出・ステージ順序制御を**ピュアなドメインロジック**として Web/DB から分離して実装する(AI-DLC の「本質的複雑性へのフォーカス」に従う。このアプリ自体を AI-DLC で開発するデモにもなる)。
- フレームワーク等の具体選定は実装計画時に決定する(技術的決定の後ろ倒し)。

## 9. エラーハンドリング

- YAML テンプレートは読込時にスキーマバリデーションし、不正定義は起動時に明示エラーで止める(黙って壊れない)。
- 承認の同時競合は楽観ロックで後勝ちを拒否する。
- 成果物リンクは URL 形式のみ検証(到達性チェックはしない)。

## 10. テスト戦略

- ドメインロジック(ゲート通過判定、孤児検出、契約変更の影響 Unit 算出、要更新の下流伝播、警告型リスクの引き継ぎ)を**ユニットテストで網羅**する。
- 画面は主要フロー(PRFAQ 確定 → Inception 進行 → 契約確定 → 機能追加ゲート)の E2E を最小限。
- テンプレート YAML のスキーマバリデーションのテスト(正常系・異常系)。

## 11. 課題→機能対応表(検収観点)

| 課題 | 対応機能 | 画面 |
|------|---------|------|
